# Working on CharCraft

These rules apply to every crate in this repository (and to `anicraft-libs` and `anicraft`, the two sibling
repositories of the family). They combine the namtao.com/rust strict lints, the conventions of the storytold Craft
apps (PhotoCraft, VectorCraft, EffectCraft, FilmCraft) and the project owner's own rules. CI enforces most of them.
The shared engine crates (`anim-*`) live in `anicraft-libs`; read its `AGENTS.md` and `ARCHITECTURE.md` for the
engine side. This repository holds the Character Animator side: `charcraft-*` crates and the apps.

## Clean room

- Behaviour only, from public specs and our own observation of files we are allowed to read. Never copy code,
  shaders, icons, fonts, sample files or other assets from Adobe products, and never decompile Adobe binaries.
- Reverse engineering of file formats (`.puppet`, `.chproj`, `_archive_info`, `Rope10LM` blobs, `.arf` takes) is for
  interoperability only and is done from sample files. Sample files from users are never committed (they live
  outside the repo; tests that need them read `ANICRAFT_SAMPLES` and return early when it is unset). Committed
  fixtures are generated by our own code or written by hand.
- Code reused from the Craft repos (MIT OR Apache-2.0) is fine: depend on the crate by git rev, or copy a module
  with its notice and add a row to `ATTRIBUTION.md` in the same commit.

## Code rules

- No panics outside tests: `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!`, `unreachable!`, indexing and
  slicing (`v[i]`, `&s[a..b]`), unchecked integer arithmetic and `as` casts are denied by clippy. Use `get`,
  `checked_*`/`saturating_*`, `try_from`, iterators, and `?` with typed errors. Float/integer conversions go through
  `anim_core::num`. Inside `#[cfg(test)]` these lints are allowed.
- Treat every file as hostile input: bound recursion depth, cap allocations, never trust lengths and offsets.
  Every crash fix gets a regression test.
- No `unsafe` in our crates (`unsafe_code = "forbid"`). Dependencies may use it. The one exception is
  `charcraft-ndi`, which calls the NDI runtime it loads at run time (`unsafe_code = "deny"`, allowed in `ffi.rs`
  only, every other workspace lint repeated in its manifest).
- No shared mutable state: no `Arc`, `Mutex`, `RwLock`, `Rc`, `RefCell` (clippy `disallowed-types`). Background work
  (camera, face tracking, microphone, playback, recording) runs in an actor (a thread or task that owns its state)
  and talks to the UI over channels (`std::sync::mpsc` or `crossbeam-channel`). If a dependency's API forces one of
  these types on you, confine it to the smallest scope with
  `#[expect(clippy::disallowed_types, reason = "...")]`.
- UI is a pure function of state: `ui(&State) -> Vec<Command>`. Event handlers translate input into commands at
  once; state changes only by applying commands; undo is a snapshot of the document model. Never read widget or
  DOM state back later.
- Don't invent serialization. Plain `serde` derives with `serde_json` (human readable) or `postcard` (binary).
  Custom readers and writers exist only for foreign formats we must be compatible with (Character Animator
  `.puppet`/`.chproj`, the Lua-table `ltab` text, `Rope10LM`, PSD, AI/PDF...).
- Libraries return `thiserror` errors; binaries use `color-eyre` (or `anyhow`) at the edge.
- Prefer crates from blessed.rs and the Craft repos. Ask in your report before adding anything else, unless there is
  no blessed option for the job (then say why in the commit message).
- Times are `anim_core::Tick` (re-exported from `filmcraft-time`: i64 at 254 016 000 000 per second, the Craft
  convention) or frame indices; never `f32` seconds in models.
- Text must support right-to-left scripts (Hebrew, Arabic) and bidi mixing everywhere text is shaped, edited,
  displayed, stored or exported. Names of puppets, layers, triggers and takes are arbitrary Unicode.
- Small crates: one responsibility each, so they compile in parallel and agents don't collide.
- Must build and run on macOS, Windows and Linux. Use `std::path`, never hard-coded separators; no shelling out to
  platform tools; gate platform code with `cfg` and keep a working fallback.

## Apps

- Both the GUI app and the CLI are thin shells over the same command registry (`anim-session`): anything the GUI can
  do, the CLI and the MCP (Model Context Protocol) interface can do, through the same commands and the same typed
  results. No behaviour lives only in a widget.
- Every GUI app supports `--screenshot OUT.png`: open the window, load the given file, wait for rendering to
  settle, request the egui screenshot, save the PNG and exit. Use `DISPLAY=:1` for a real window when testing on
  the build machine.

## Tests

- Unit tests next to the code, integration tests in `tests/`. Round-trip tests for every format (`read(write(x)) == x`)
  and golden tests for rendering (small PNGs, compared with a tolerance). Where a sample file exists, also test
  byte-exact re-serialization, skipped when `ANICRAFT_SAMPLES` is unset.
- Run builds through the queue (see below) in the dev profile. Use release only for benchmarks.

## Visual verification: predict, render, inspect

Every component that draws, deforms or animates a puppet follows the predict → render → inspect loop described in
anicraft-libs' AGENTS.md ("Visual verification"):
- Hand-written, original synthetic puppets in `tests/fixtures/visual/`, each targeting a failure mode. For this repo:
  head turned and moved to the limits while welded to the body, limbs with IK at full stretch, draggers pulled far
  away, dangles, blinks and visemes swapped mid-motion, overlapping independent groups, nested warps.
- A written prediction in `<name>.expect.md` before rendering, for example "the neck stays connected: no transparent
  pixel along the neck line".
- Close inspection of every PNG with the Read tool, using crops.
- Fix the code, not the prediction.
- Assertions plus goldens at the end.

## After it is correct: profile, then simplify

Follow anicraft-libs' AGENTS.md section of the same name:
- Benchmarks and real profiles (perf, samply or flamegraph) on the sample puppets and stress fixtures.
- Optimisations backed by measurements.
- Deletion and deduplication.
- Moving helpers shared with other crates into anicraft-libs (anim-core or a small shared crate) and deleting the
  local copies.

## Building: always through the job queue

Never run `cargo` directly for builds, checks, clippy or tests. Use the queue so parallel agents share the machine:

    /mnt/data/anim/tools/q -p <priority> -- mbx clippy -p <crate> --all-targets -- -D warnings
    /mnt/data/anim/tools/q -p <priority> -- mbx test -p <crate>
    /mnt/data/anim/tools/q -g heavy -p <priority> -- mbx build -p <app>        # full app links, packaging

`mbx` wraps cargo with a shared compile cache. Cheap commands (`cargo metadata`, `cargo fmt`, `git`) run directly.
Before landing, also check that the crate compiles for the other platforms:

    /mnt/data/anim/tools/q -p <priority> -- mbx check -p <crate> --target x86_64-pc-windows-msvc
    /mnt/data/anim/tools/q -p <priority> -- mbx check -p <crate> --target aarch64-apple-darwin

(Crates with C build scripts may fail to cross-check for lack of a C toolchain; say so in your report instead.)

## Editing and landing

- Create and modify files only with the Edit and Write tools, never with shell redirection, `sed`, `cat <<EOF`,
  scripts or `cp`. `cargo fmt` is allowed.
- Work in your own git worktree on your own branch.
- Commit often, in small atomic commits (one logical change each, tests passing), with Conventional Commit messages:
  `feat(charcraft-ltab): parse Lua tables`, `fix(charcraft-rope): tolerate truncated records`,
  `test(...)`, `refactor(...)`, `docs(...)`, `build(...)`, `ci(...)`, `chore(...)`. The scope is the crate name.
  Never add Co-Authored-By or any other AI attribution to commits.
- Land with `/mnt/data/anim/tools/land -p <priority> -- <check command>`: it rebases on `origin/main`, re-runs your
  check through the queue and pushes straight to `main`. There are no pull requests.
- Only touch your own crate's directory unless your task says otherwise. Adding a dependency to the root
  `[workspace.dependencies]` is fine.
